# Durable wake decisions

Wake decisions are deterministic coordination primitives for a trusted host. They make no model calls. The optional `ContinuationDispatcher` below connects a continuation grant to an operator-installed launcher. All `Application` wake methods require current project admin access, run under the project transaction lock, and are deliberately absent from the MCP catalog. Unregistered tickets never produce wake decisions. Both supplied adapters support the optional capability `wakeDecisions: true`.

`registerWakeCondition(actorId, projectId, input)` creates one durable lane per ticket. Supply the ticket UUID and either `{kind:'events', types:[...]}` or `{kind:'continuation', continuation_id:'...'}`, plus an optional UTC `deadline`. Continuations must belong to the same project and ticket. Event types are explicitly limited to `ticket.updated`, `ticket.invalidated`, `ticket.transitioned`, `ticket.note_added`, `ticket.linked`, `ticket.reviewed`, `ticket.submitted`, `work.released`, `run.submitted`, and `run.settled`. The selector applies only to that ticket's events. Heartbeats cannot be registered. An identical registration retry returns existing state without resetting its cursor or observed conditions.

`evaluateWakeConditions(actorId, projectId, {ticket_id?, after?, limit?, event_limit?})` reads at most 100 registrations and 100 durable events per registration per pass (defaults 100 each). Follow `next_cursor` while `has_more` is true; begin another sweep at the start afterward. The companion rotates these pages automatically. Supply `ticket_id` instead of `after` to evaluate one registered ticket directly; the continuation dispatcher uses this bounded path so other registrations cannot starve its target. Each registration retains its own durable event cursor, so restarting a sweep after reconnect cannot skip events. Registration begins at the project's current committed sequence; it does not replay pre-registration event history.

Events are processed in sequence order. A cursor advances only in the transaction that also persists observed fingerprints and pending reasons. Event-ID replays fall behind the cursor. Repeated identical latest payloads for a selected event type are suppressed using canonical hashes; no source body is stored in the decision. Relevant event bursts merge into one reason per event type, retaining their first/last sequence and distinct-observation count. The sequence interval remains an attributable reference to the original durable events. Unrelated events and heartbeats can advance the cursor without requesting a decision. Missing event sequences fail with `EVENT_GAP` and roll back cursor advancement; restore the missing durable history before resuming.

Continuation settlement and deadline expiry are also checked directly against durable state each pass, even while an unrelated event backlog is being drained. A settled continuation produces its IDs, `satisfied`/`failed` state and a bounded result code. A deadline produces its UTC timestamp. These observations are latched once until an explicit rearm. They survive restart and stay queued until consumed; no model polling is needed. Companion evaluation occurs between script runs, so long foreground executions can delay observation until the next pass.

`getWakeCondition(actorId, projectId, ticketId)` reads the registration, pending reasons and any active grant. `claimWakeDecision(actorId, projectId, {ticket_id, expected_generation})` atomically creates one grant with a new monotonic generation, random token, safe observed cursor and timestamp. It returns null when there is no eligible pending work or another grant remains active. Ordinary event reasons wait for cursor catch-up so finite bursts coalesce across bounded pages. Already observed `run.settled` events (failed or satisfied), continuation states and deadlines can be claimed at their observed cursor despite newer traffic; unrelated partial event reasons stay queued until catch-up. Terminal event grants retain only the event type and sequence references, without copying event data. Continuous traffic therefore cannot starve an observed terminal condition or deadline, though it can defer ordinary event consumption. A stale expected generation fails with `VERSION_CONFLICT`.

`finishWakeDecision(actorId, projectId, {ticket_id, generation, token})` clears only that exact active grant. Its identical retry succeeds without another audit event. An old token cannot finish a newer generation. Events arriving during an active grant accumulate separately and become eligible only after it finishes. There is no automatic lease expiry or takeover: a disconnected consumer's uncertain work remains active. The consumer must durably retain its grant and establish completion before finishing it; these primitives alone do not establish exactly-once execution of an external model or process. Admin reads can recover the persisted grant after reconnect.

Explicit rearm uses `registerWakeCondition` with the exact current `expected_revision`. It requires a drained cursor, no pending reasons, no active grant, and no unobserved expired deadline or settled continuation. Rearm preserves the generation counter and resets observations only after these checks. Every consumed grant records `wake.claimed` and `wake.finished` audit events. Claimed audit payloads contain reason codes, IDs, sequence ranges and timestamps; consumption tokens, ticket bodies, prompts and process artifacts are excluded.

Apply PostgreSQL `019_durable_wakes.sql` or SQLite `011_durable_wakes.sql` before starting a capable runtime. Existing tickets and runs receive no implicit registrations. Keep the durable event stream with its cursors when backing up or restoring. Custom adapters must implement the table/codecs and atomic project transactions before advertising the capability.

## Opt-in continuation dispatch

`ContinuationDispatcher` is a provider-neutral trusted-host seam, exported from the package. Construct it with the application, shared `HostCapacity`, admin actor/project/host IDs, and an operator-installed synchronous `launch(context, invocation)` callback. It installs no provider, command runner, CLI loop or network invocation. The context contains canonical work IDs and the current registered client selection; ticket bodies, checkpoints and artifact bytes never supply executable instructions. The launcher owns process/provider containment, claim and host-capacity heartbeats, and independent termination/usage observation.

Call `runOnce({ticket_id, predecessor, budget_run_id, provider, allowance})` from the trusted host's wake handling. `predecessor` is the exact host/queue/execution-token identity of the original agent in that same local capacity ledger. A continuation must be explicitly registered. Each pass deterministically evaluates durable wakes and claims or resumes its existing generation. Completion notifications alone cannot satisfy a pending continuation. A satisfied condition remains latched while its predecessor is running or unresolved, or the host is full. These waits make zero launcher/model calls. The predecessor must have a matching independently reconciled terminal observation; lease expiry or takeover alone never proves exit.

Before admission, the application checks current worker authorization, work claim/assignee, requirements revision, blocking questions/dependencies, and the exact live registered client pin. It verifies published artifact ownership against the execution attempt, result outcome against durable settlement, and actual artifact bytes against their hashes under the artifact-retirement lock. Missing, altered or expired artifacts stop dispatch. The host admits the continuation through existing agent-slot and usage-budget fences, using a deterministic queue/attempt identity per continuation generation. Unsupported execution choices, unresolved approvals, expired deadlines, stale ownership/requirements and budget failures persist `needs_attention` on the active grant. Queued capacity is cancelled when a generation needs attention before admission.

Admission commits a `starting` intent to the active grant's existing JSON before any launcher call, requiring no migration. Only the call that created that intent can continue to launch. A second project transaction repeats live authorization, ownership, capability and artifact checks; the host rechecks predecessor proof, capacity ownership and unchanged budget accounting immediately before the synchronous callback. Successful callback return records `running`. A thrown launcher or failure after admission retains its invocation identity and occupied capacity for investigation. A crash between intent commit and callback leaves `starting`, which means launch is uncertain. Replays and restarts never invoke `starting`, `running`, `completed` or `needs_attention` generations again. There is no automatic retry or takeover launch.

Use `dispatcher.reconcile(fence, observation)` only with independent supervisor/provider evidence for that invocation's exact execution token and usage settlement. It reconciles the current capacity lease and records `completed`; repeated identical evidence is idempotent. A `never_started` proof requires a cancelled outcome, zero runtime and observed zero input/output tokens. Unknown usage stays charged and blocks later work as the budget ledger specifies. Only then may the admin finish the exact wake fence and explicitly rearm. A `needs_attention` generation without an admitted invocation may be explicitly finished after operator review; an admitted or uncertain invocation cannot be finished until reconciled. Recovery does not infer exit from worker-authored completion text, a timeout, cancellation request or missing acknowledgment.

The local capacity transaction can commit before the ticket-store intent transaction. On restart, the committed wake generation determines the exact queue/attempt ID. Before budget checks or launch authorization, the dispatcher recovers an existing occupied admission only when host, project, budget run, attempt, worker, ticket and requirement identities match. It records `ADMISSION_UNCERTAIN` with the original execution token, including when the worker claim has since expired. It never launches that admission again or refunds its usage. Missing or still-queued admissions can re-drive normal validation; mismatched identities require attention without adopting an unrelated token.

Before touching capacity, the application commits a waiting admission marker that prevents finishing the generation across a ticket-store rollback. Errors after admission re-inspect the exact local queue before recording attention; older attention records with a missing invocation are also inspected on replay. An attention record without an invocation is finishable only when `admission_uncertain` is explicitly false. Missing legacy proof, a host/budget mismatch or an unavailable ledger remains fenced until exact admission inspection or independent reconciliation resolves it.
