# Explicit artifact retention

On Linux, an operator can retire one unreferenced terminal stdout/stderr capture using verified directory handles. Nothing runs automatically, and no MCP profile exposes deletion. Use the same store, absolute artifact root and artifact TTL as the MCP service:

```powershell
node dist/execution-companion-cli.js --sqlite STORE --actor ADMIN --project PROJECT --artifacts ABSOLUTE_ROOT --retire execution:RUN_UUID:ATTEMPT_UUID:stdout
```

PostgreSQL uses the configured `DATABASE_URL` instead of `--sqlite`. Migrate with schema-owner credentials before restarting services; this adds PostgreSQL `023_artifact_retention.sql` or SQLite `015_artifact_retention.sql`. The trusted SDK equivalent is `Application.retireExecutionArtifact(actorId, projectId, artifactId)`.

Retirement requires current project-admin authority, a published exact run/attempt identity, completed reconciliation, and an unchanged trusted `result.json`. Both the journal's finish time and durable run settlement must have passed the configured TTL. The journal must confirm cleanup, match the authoritative outcome, and contain the exact capture size and SHA-256. Missing legacy proofs, changed files, links, unresolved effects or uncertain ownership refuse deletion.

Active ticket work pins its run. Within the run's project, stored ticket content, notes, evidence and audit history still pin matching artifact, run or attempt identities. Across projects, a write containing an exact published artifact ID records a durable pin only if its author can read the source project. A bare run or attempt UUID has no effect across projects. Pins do not grant access to the underlying bytes. Older free-text citations lack a durable authorization record. After upgrading, re-record valid older cross-project citations through authorized ticket notes before running retirement. Current and historical same-project knowledge and provenance remain pins after edits or archival.

Pin checks run through database `EXISTS` queries. Only actual reference writers and artifact/run retrieval acquire the shared artifact lock; retirement acquires its exclusive counterpart. Normal heartbeats do not acquire that lock. SQLite retains its existing write serialization. New references to retired execution identities or memory sources are rejected even on a service without filesystem artifact configuration. Identical committed mutation receipts retain their original authorized replay behavior.

The immutable retirement decision and `artifact.retired` audit event commit before unlink. A second authorized transaction rechecks references, root identity, file identity, hash and expiry, then unlinks that exact file and records `artifact.deleted`. A crash between phases leaves the file protected by a durable decision; repeat the same explicit command after restart. A crash after unlink resumes with the file already absent. Retired reads return explicit `expired` metadata, including the original capture hash and size, without bytes. Changing the configured root or TTL can refuse a pending retry; restore the original configuration before retrying.

The command never removes directories, receipts, submissions, knowledge revisions, execution history, `outcome.json`, or private recovery journals such as `result.json`, `pipeline-report.json` and `pipeline-timeout.json`. Temporary files are refused: current writers do not publish enough lifetime proof to authorize deleting an orphan safely. No recursive deletion or caller-supplied filesystem path is accepted.

Pinned artifacts remain readable after the configured TTL. Authorized reads first honor immutable retirement decisions, then check durable pins only when the ordinary artifact read would expire. Pinned reads return available bytes and hashes with no scheduled expiry; unpinned reads retain their normal expiry. The same rule applies to bounded run status, omission recovery and failure-location evidence.

Physical cleanup is currently supported only on Linux with `/proc/self/fd`. Windows and other platforms return `UNSUPPORTED_PHYSICAL_CLEANUP` before committing a new retirement decision. A previously committed Linux decision remains immutable on those platforms and returns `retired_pending` with `reason: unsupported_physical_cleanup`; its bytes are retained for a supported operator to finish.

Linux opens and verifies owned root/run/attempt directory handles without following links. All staging, restoration and unlink names are relative to those held handles, so replacing a pathname parent cannot redirect cleanup outside its verified physical directory. Captures first move atomically into the owner-only `.retired-stdout` or `.retired-stderr` directory. A fsynced `decision.json` binds that directory to the immutable decision before staging; exact inode, regular-file shape, single-link ownership, size and hash are checked again before unlink. Private staging directories and markers remain as audit/retry journals. The root and these private staging directories must have one cooperating OS owner; recipes and other writers must never mutate the staging directories. The shared database lock serializes participating reference writers and readers, not arbitrary privileged filesystem edits.

A crash after staging but before unlink resumes from the bound capture after restart. A crash after creating a staging directory but before publishing its marker never unlinks the capture and returns `ARTIFACT_STAGING_CONFLICT`; inspect the named private directory before retrying. If a source is replaced during staging, cleanup refuses to delete the replacement. It restores the original name with a no-overwrite hard link when vacant and retains quarantined bytes; if occupied, both locations remain untouched. Inspect and resolve that explicit conflict rather than automatically deleting temporary files. Candidate and marker opens are nonblocking, so substituted FIFOs are rejected without stalling the retention lock.
