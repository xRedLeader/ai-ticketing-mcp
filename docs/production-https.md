# Production HTTPS

The supported public entry point is [deploy/Caddyfile](../deploy/Caddyfile) with [deploy/compose.production.yaml](../deploy/compose.production.yaml). Caddy obtains and renews publicly trusted certificates and redirects HTTP to HTTPS. App and Keycloak traffic inside the private Compose network remains HTTP. MCP tools contain no certificate or HTTPS logic.

## Operator setup

Use Node 24+, Docker, and Docker Compose 2.24.4+ (`!reset`/`!override` support). Keep the same checkout directory or explicit Compose project name on every invocation so the named volumes stay attached. Run `node scripts/setup.mjs` to generate distinct passwords. It preserves an existing `.env` and reports any remaining example passwords. Edit that private file with the actual operator-owned hostnames below. Preflight rejects example domains and weak or reused passwords. If an existing installation ever used the example credential, rotate the actual Keycloak administrator password through Keycloak and the affected database roles through PostgreSQL. Editing the Compose environment alone does not rotate existing credentials.

```dotenv
TICKETING_DOMAIN=tickets.example.com
LOGIN_DOMAIN=login.example.com
PUBLIC_URL=https://tickets.example.com
OAUTH_AUDIENCE=https://tickets.example.com/mcp
KEYCLOAK_PUBLIC_URL=https://login.example.com
OAUTH_ISSUER=https://login.example.com/realms/ticketing
OAUTH_JWKS_URL=https://login.example.com/realms/ticketing/protocol/openid-connect/certs
ALLOWED_ORIGIN_HOSTS=tickets.example.com
```

`PUBLIC_URL` is an origin without a trailing slash, credentials, path, query or fragment. The audience is the exact unqueried `/mcp` URL, including scheme/hostname/case; `/mcp?profile=worker` still uses that audience. The issuer is the exact external Keycloak realm URL, with no trailing slash. The app resolves the login hostname to Caddy on the Compose network and fetches signing keys with normal HTTPS certificate validation. Register actors with that same public issuer and the immutable Keycloak subject, then grant project memberships as described in [authentication](authentication.md#included-keycloak-setup). Migrating a local realm to a new issuer requires deliberate actor registration/grants; old local issuer identities do not automatically become public identities.

`ALLOWED_ORIGIN_HOSTS` is a comma-separated list of explicit trusted browser hostnames, including the ticketing hostname. Add only hosts actually used by trusted MCP clients. It is a hostname allowlist, not a list of URLs; do not use `*`, schemes or ports. Configure human clients' exact callback URLs in Keycloak separately. OAuth scopes and project roles are still required.

1. Create public A records for both hostnames pointing to this host's public IPv4 address. If publishing AAAA records, route IPv6 to the same Caddy service too; remove stale AAAA records. Check authoritative/public DNS from outside the deployment network, for example `dig +short A HOSTNAME` and `dig +short AAAA HOSTNAME` (or `Resolve-DnsName HOSTNAME`). A local hosts-file entry does not establish public DNS.
2. Forward and allow inbound **TCP 80 and 443** through cloud firewalls, host firewalls, NAT and load balancers. Allow Caddy outbound DNS and HTTPS to the certificate authority. Port 80 serves redirects and ACME HTTP challenges; 443 serves MCP/login and can serve TLS challenges. Test every published A/AAAA address externally. A successful check from the host can reflect split DNS or NAT loopback and does not prove public reachability. Check CAA policy permits Caddy's configured issuer if CAA is present.
3. Prepare the new-install realm and validate the merged configuration without printing secrets:

   ```sh
   node --env-file=.env scripts/check-production.mjs --prepare-realm
   ```

   This writes ignored `.local/keycloak-realm.production.json` with the exact audience. Run this step for both new and existing installations: the production override requires this regular file as its read-only import mount. Preflight checks it even when `--realm-file` supplies a current export. It does not start services or change a running realm. On first startup, the bundled clients receive `ticketing:read` and `ticketing:write`; `ticketing:read` carries the access-token audience mapper. Read client secrets only in the private administration console.

   The generated import contains only allowlisted public template settings and is atomically replaced with mode `0644`, including under a restrictive umask, so Keycloak UID 1000 can read a file generated by another user. Re-run `--prepare-realm` to repair earlier `0600` imports. Private current exports supplied through `--realm-file` are only read for validation; their contents and permissions are never copied into the public import.

4. **Existing Keycloak realm:** startup `--import-realm` skips an already existing realm. In the administration console, select `ticketing` → Realm settings and clear any old Frontend URL override (or set it to the exact `KEYCLOAK_PUBLIC_URL`). Otherwise that realm setting can override `KC_HOSTNAME` and advertise the wrong issuer. Then select Client scopes → `ticketing:read` → Mappers → `ticketing-audience`. Set Included Custom Audience to the exact `OAUTH_AUDIENCE` and enable Add to access token. Ensure each intended MCP client's effective/default scopes include `ticketing:read` and, for writers, `ticketing:write`. Export the current realm including client scopes/clients to a private ignored file, then validate it:

   ```sh
   node --env-file=.env scripts/check-production.mjs --realm-file .local/current-realm.json
   ```

   The export can contain private provider/client configuration; never commit or attach it to a ticket. A passing import-template check alone proves nothing about an already imported realm. The checker verifies the supplied export, not the live admin API. Obtain a fresh token after changing scopes/mappers; old tokens retain old claims. Use Keycloak's client-scope evaluation view to verify that the intended clients receive the exact `aud`, public `iss`, and requested scopes without copying access tokens into logs.

5. Start the production stack from the repository root:

   ```sh
   docker compose -f compose.yaml -f deploy/compose.production.yaml --profile auth --profile local-ai up -d --build
   node --env-file=.env scripts/check-production.mjs --live
   ```

   For an existing realm include `--realm-file .local/current-realm.json` on the live check too. The override disables host publication of PostgreSQL, app, Keycloak and Ollama ports. Only Caddy publishes 80/443; Keycloak's management interface stays private. Limit administration-console access through your operator network/access controls. Do not add public backend port mappings to bypass Caddy.

The preflight reports field names and remedies without echoing `.env`, rendered Compose JSON, tokens, or provider errors. Avoid publishing `docker compose config` output: it contains expanded passwords. Offline preflight checks the URLs, assigned audience mapper, intended clients/scopes, backend bindings and persistent proxy volumes. `--live` also checks DNS through the current system resolver, port-80 redirects, normal hostname/chain/expiry-verified HTTPS, exact public resource/issuer discovery and app readiness. It refuses `NODE_TLS_REJECT_UNAUTHORIZED=0`. It does not probe every resolved address or prove external firewall routing; repeat live checks externally and test each advertised IPv4/IPv6 route.

## Smoke checks

From an external client, run the live preflight with the same private environment, or use `curl -I http://TICKETING_DOMAIN/healthz`, `curl https://TICKETING_DOMAIN/readyz`, and retrieve `https://TICKETING_DOMAIN/.well-known/oauth-protected-resource/mcp`. Expect a redirect to the same HTTPS path, readiness 200, and exact public resource and authorization-server URLs. Check `https://LOGIN_DOMAIN/realms/ticketing/.well-known/openid-configuration` has the exact public issuer. Keep normal certificate verification enabled; do not use `curl -k`.

Using a fresh token for a registered actor with project access, run the built CLI through the SDK transport:

```sh
npm run build
node dist/cli.js call --url https://TICKETING_DOMAIN/mcp --token-env ACCESS_TOKEN --operation project_list --input '{}'
```

Set `ACCESS_TOKEN` privately in the process environment; never put the token in a command argument. A response with permitted projects confirms authenticated MCP traffic. No token should produce 401 with an HTTPS `resource_metadata` challenge, a wrong issuer/audience or expired token 401, a token without `ticketing:read` 403, and a read-only token's mutation `INSUFFICIENT_SCOPE`. Recheck these after identity/proxy changes. Exercise a disposable project's create/claim/submit workflow with an appropriate writer before routing agents to production; the offline fixture below already automates this with synthetic data.

## Renewal, restart and recovery

Caddy renews automatically while it is running, with the same DNS/routing and outbound access needed for initial issuance. Persist **both** named volumes: `certificates:/data` holds ACME account/certificate private keys and certificates, and `proxy_config:/config` holds proxy state. The PostgreSQL `database` volume separately holds app and Keycloak records. Restrict and encrypt backups containing keys, realm exports or operator configuration. Preserve the original project/volume names when restoring or moving hosts. Never run `docker compose down -v` as a restart or renewal fix.

After a normal restart (`docker compose -f compose.yaml -f deploy/compose.production.yaml --profile auth restart proxy`), run the live/readiness/SDK smoke checks again. Inspect certificate expiry with `openssl s_client -connect HOSTNAME:443 -servername HOSTNAME </dev/null 2>/dev/null | openssl x509 -noout -dates -issuer -subject` from an external host; repeat for both names and all public routes. Monitor Caddy renewal errors and certificate expiry before expiration. Local tests prove persistence/restart behavior, not a future public renewal.

If renewal fails, inspect recent proxy logs locally (`docker compose -f compose.yaml -f deploy/compose.production.yaml --profile auth logs --tail=100 proxy`) for DNS/challenge/network/CAA/rate-limit/storage errors. Check clock accuracy, all A/AAAA routes, public 80/443, outbound ACME HTTPS/DNS, CAA policy and volume free space/permissions. Correct the cause, retain the existing certificate and account volumes, then let Caddy retry or restart only the proxy and repeat smoke checks. Respect CA retry/rate-limit times; deleting volumes and repeated issuance attempts can worsen the outage. If keys/state were lost, restore the protected volume backup first; fresh issuance is required only when recovery is impossible. If the certificate has already expired, repair issuance before resuming clients; never bypass their certificate checks. Do not rotate identities or erase the database to repair TLS.

## Automated local evidence and public prerequisites

Run `npm ci`, `npm test` and `npm run test:https` with Node 24 and Docker available. CI runs the HTTPS and fresh Keycloak import fixtures. It fails when Docker/Caddy is unavailable rather than silently skipping. [tests/production-config.test.ts](../tests/production-config.test.ts) covers invalid configuration, stale realm audience, missing client scopes, exposed backend ports and missing TLS volumes. [tests/https/caddy.test.ts](../tests/https/caddy.test.ts) runs the actual production Caddyfile's site blocks with private upstream addresses remapped to ephemeral fixture ports. The fixture app uses `localhost` and its mock login uses `127.0.0.1`; a test-only `default_sni 127.0.0.1` selects the login certificate for IP clients that omit SNI. Caddy uses a temporary **internal test CA**, not public issuance, on loopback-published random high ports. The Node backend fixture binds ephemeral host ports so the container can reach it; run this test on a trusted development/CI host.

[tests/https/keycloak.test.ts](../tests/https/keycloak.test.ts) stages the import on Linux storage as root with umask `077`, checks fresh and existing `0600` files, excludes private template fields, and preserves a private export behind a stale import symlink. It starts the exact Keycloak image and command from merged production Compose with the same read-only file bind mount and default UID 1000, using a disposable embedded database and loopback port. It verifies a fresh realm import and the public discovery issuer, then removes its container and staging volume. This fixture also requires the `node:24-alpine` image.

[tests/https/client.ts](../tests/https/client.ts) starts in a child process with only that process's `NODE_EXTRA_CA_CERTS` pointing at the temporary root. It uses real SDK protected-resource and authorization-server discovery and `Client`/`StreamableHTTPClientTransport` calls over TLS. It checks HTTP redirect/path/query preservation; separate untrusted-chain and `ERR_TLS_CERT_ALTNAME_INVALID` failures; missing/expired/wrong-audience/wrong-issuer auth; read/write scope and origin rejection; create/claim/submit completion; catalog/resource/result equality across direct HTTP and TLS; and canonical structured/text envelope equality. The harness also restarts Caddy against the same named volumes, checks the CA fingerprint is unchanged and readiness still works, then confirms gap-free closed protocol capture includes SDK operations and excludes Authorization headers and all bearer tokens. It cleans up only its uniquely named test containers/volumes and verified temporary directory. No global trust store is changed and verification is never disabled.

The fixture uses SQLite and a synthetic signed-JWT/OIDC server to test the transport boundary. It does not replace PostgreSQL integration tests, a real Keycloak login, public ACME issuance, long-duration renewal, or external DNS/firewall validation. Those public checks remain pending until an operator supplies the real domain names, DNS records, public host/firewall routing and identity-provider/client configuration. Record the deployment's actual source revision and the results of live preflight plus authenticated SDK smoke checks before declaring public HTTPS operational.
