# SQLite hot reload preflight

`readSqliteMigrations(entry)` captures a sorted, frozen snapshot of migration filenames and exact bytes. Migration contents are stored as immutable base64 strings. A build may append newer filenames, preserving every earlier file byte for byte. An exact prefix rollback is accepted only when every omitted migration passes the same expansion rules; rollback never reverses schema changes. Identical and already-applied histories still validate persisted provenance read only and need no database copy.

`prepareSqliteReload(previous, next, filename)` rejects edits, renames, reordered history, and SQL outside this narrow grammar:

```sql
CREATE TABLE extra_records(id TEXT PRIMARY KEY, body TEXT NOT NULL);
ALTER TABLE tickets ADD COLUMN future_field TEXT;
```

Identifiers must be ASCII names, optionally double quoted. Column types are `TEXT`, `INTEGER`, `REAL`, `BLOB`, or `NUMERIC`. New table columns may use `PRIMARY KEY`, `UNIQUE`, `NOT NULL`, `NULL`, and `DEFAULT NULL`. Added columns must remain nullable and may only specify `NULL` and `DEFAULT NULL`. Ordinary comments and statement delimiters are recognized. New tables cannot reference old tables or run expressions. Protected names are `schema_migrations`, `_mcp_hot_reload_migrations`, `sqlite_*`, and `search_*`, case insensitively.

Other SQL requires a controlled upgrade: rebuilds, drops, renames, data changes, indexes, triggers, views, virtual/temporary tables, qualified names, `IF NOT EXISTS`, checks, foreign keys, generated columns, and non-null defaults. SQLite itself validates accepted statements against a consistent temporary backup, including existing schema conflicts. The trial transaction always rolls back, leaving a pristine backup for the candidate to run its normal startup migrations. On success the helper returns `{ filename, apply, dispose }`; the caller must close the candidate before disposing. Rejected probes clean up their temporary files. Preflight opens the live database read only.

The backup lives in a new `.ticketing-sqlite-reload-*` directory beside the resolved database path. On Unix the directory and copy are restricted to the owner. On Windows the copy inherits access controls from the database directory, so keep that directory private to the server account. A crash can leave the copy behind. Remove such directories only after confirming that no launcher is using them.

Only after the operator allows expansion and shadow discovery succeeds may the caller invoke `apply()`. It revalidates current history under `BEGIN IMMEDIATE`, applies the approved SQL, records migration names, and persists the complete name/SHA256 history in `_mcp_hot_reload_migrations` in one transaction. Failures roll back SQL and both ledgers together. Matching repeat calls are idempotent; a competing migration with different bytes or omitted known files is rejected. A failed later candidate startup leaves the committed expansion in place so the old build can keep running and a fresh relay can recognize the same approved files. Ordinary candidate startup then finds those names already applied.

The existing adapter writes explicit column lists, so these nullable additions preserve its ordinary reads, writes, and idempotency receipts. This is a schema compatibility boundary, not a proof about arbitrary application code or custom data. Positional `INSERT INTO table VALUES(...)`, `SELECT *` consumers, custom triggers, externally supplied SQL, and new handlers with different business rules need separate review. Existing custom schema can also cause SQLite to reject an otherwise allowed addition. A controlled upgrade is appropriate when compatibility depends on those behaviors.

SQLite's original migration ledger stores filenames rather than content digests. On first apply, the caller's captured previous build is the trusted baseline; its applied names must match exactly before its hashes are recorded. Earlier file contents cannot be recovered or proven from SQLite alone. A suffix name already applied without matching persisted provenance is rejected. Once recorded, the full manifest must match the applied names, every candidate must preserve its exact prefix, and new expansion must resume the highest known history even after rollback. A successful expansion is never undone. Deployment artifacts must remain immutable while candidates start, and the caller must verify the captured migration bytes before exposing a candidate. This helper does not sandbox candidate code. Inputs are bounded to 1,024 migration files, 1 MiB per file, and 16 MiB total, with valid UTF-8 required.
